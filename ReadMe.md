## How does it work

### Approach 1: Use the default WinUI VB XAML compiler
The MSBuild target files of WinUI 3 need some hacking to support Visual Basic.
VB projects need to import the following two files to use WinUI 3.

**WinUI3.VisualBasic.props**
```xml
<Project>
  <PropertyGroup>
    <!-- Workaround for conflicts with WPF -->
    <ImportFrameworkWinFXTargets>true</ImportFrameworkWinFXTargets>
  </PropertyGroup>
</Project>
```

**WinUI3.VisualBasic.targets**
```xml
<Project>

  <!-- Workaround for XamlPreCompile compilation errors -->
  <Target Name="SpecifyVBRuntimeForXamlPreCompile" BeforeTargets="XamlPreCompile">
    <PropertyGroup>
      <VBRuntime>None</VBRuntime>
    </PropertyGroup>
  </Target>

  <!-- Run without MSIX packaging: self-contained runtime, no auto bootstrap -->
  <PropertyGroup Condition="'$(WindowsAppSDKSelfContained)'=='true'">
    <WindowsAppSdkAutoInitialize>false</WindowsAppSdkAutoInitialize>
    <WindowsAppSdkUndockedRegFreeWinRTInitialize>false</WindowsAppSdkUndockedRegFreeWinRTInitialize>
  </PropertyGroup>

</Project>
```

The `Sub Main` entry point is generated by the compiler, so no `Program.vb` is needed. To take it
over manually, define `DISABLE_XAML_GENERATED_MAIN` and call the generated
`XamlGeneratedProgram.XamlGeneratedMain()` from your own `Sub Main`.

## Samples
### BatchFfmpegWinUI
A `mp4` video to `h265` transcoder.

It converts `.mp4` and `.mkv` videos to `h265` encoding by calling `H265.bat`.

#### Status
✅
Finished. Builds and runs with Windows App SDK `2.2.0`; XAML is compiled by the forked compiler.

#### How to use it
- Install `ffmpeg` to `%programfiles%\ffmpeg\bin`. If you have installed it in a different location, please add it to `%PATH%`.
- Open `BatchFfmpegWinUI.sln` with Visual Studio.
- Set `BatchFfmpegWinUI_Pack` as startup project and run.
- Drag and drop `.mp4` or `.mkv` files.
- Press the "Convert" button and wait.

### Custom XAML compiler
The compiler is built from [winui3-vbxamlc](https://github.com/Nukepayload2/winui3-vbxamlc), a fork
of `microsoft-ui-xaml` whose Visual Basic code generators are fixed, and consumed as a
compiler-only NuGet package (`Nukepayload2.UI.VBWinUI3.XamlCompiler`) from a local folder feed.

The package carries only `tools\net8.0\` (7 files), `tools\net472\` (19 files), `tools\NOTICE.txt`,
one `buildTransitive\<PackageId>.props` and a readme. The file names match the stock
`Microsoft.WindowsAppSDK.WinUI` tools folder; only the Core-MSBuild folder is renamed from `net6.0`
to `net8.0`. Targets, `genxbf` and the reference assemblies keep coming from the stock package.

Its props are imported through `obj\<project>.nuget.g.props`, before
`Microsoft.UI.Xaml.Markup.Compiler.interop.targets` assigns its three tool paths behind empty-value
guards, so the package's assignments win:

| Property | Stock default |
| --- | --- |
| `XamlCompilerTaskPath` | `$(_MuxPackageToolsFolder)Microsoft.UI.Xaml.Markup.Compiler.dll` |
| `XamlCompilerJsonTaskPath` | `$(_MuxPackageToolsFolder)Microsoft.UI.Xaml.Markup.Compiler.IO.dll` |
| `XamlCompilerExePath` | `$(_MuxPackageToolsFolder)..\net472\XamlCompiler.exe` |

`_MuxPackageToolsFolder`, `GenXbfPath` and `XamlCompilerPropsAndTargetsDirectory` stay pointed at the
stock package. Under Core MSBuild (`dotnet build`) the compiler runs as
`Exec "$(XamlCompilerExePath)" input.json output.json`; under desktop MSBuild / Visual Studio the
`XamlCompilerTaskPath` assembly is loaded as an in-proc task.

#### Enabling it in a project
1. Reference the package (nothing else is needed - in particular no `PrivateAssets` /
   `ExcludeAssets`, which would also suppress the `buildTransitive` import that performs the
   override; `DevelopmentDependency=true` already keeps the package private):

```xml
<ItemGroup>
  <PackageReference Include="Microsoft.WindowsAppSDK" Version="2.2.0" />
  <PackageReference Include="Nukepayload2.UI.VBWinUI3.XamlCompiler" Version="3.0.0-dev" />
</ItemGroup>
```

2. Point NuGet at the local feed with a `nuget.config` in the repository root (relative paths are
   resolved against the file's own directory; no `<clear/>`, so nuget.org is still inherited). The
   feed lives inside the `vbxamlc` submodule:

```xml
<configuration>
  <packageSources>
    <add key="vbwinui3-local" value="vbxamlc\PackageStore" />
  </packageSources>
</configuration>
```

The submodule must be initialized (`git submodule update --init --recursive`) and its nupkg packed
before restoring: `PackageStore` is git-ignored, so a fresh clone has no artifact. If the submodule
is checked out somewhere else, use
`dotnet restore -p:RestoreAdditionalProjectSources=<absolute path>` rather than a bare `--source`,
which *replaces* every configured source.

#### How to tell which compiler ran
- The build log contains, even at minimal verbosity:
  `VBWinUI3 XamlCompiler override active: CompileXaml=... ; Json=... ; Exe=...`, with all three
  paths under `~\.nuget\packages\nukepayload2.ui.vbwinui3.xamlcompiler\<version>\tools\`.
- The generated `obj\...\App.g.i.vb` contains `Friend Module XamlGeneratedProgram` and
  `Sub XamlGeneratedMain()`.
- Every generated file carries
  `GeneratedCodeAttribute("Microsoft.UI.Xaml.Markup.Compiler", " 3.0.0.0")`. The stock 2.2.x
  compiler stamps `3.0.0.2606` instead, which makes this string a reliable discriminator.
- To revert to the stock compiler without editing any file:
  `dotnet build -p:VBWinUI3XamlCompilerEnabled=false`.

#### Rebuilding the package
```
:: 1. build the compiler in Release (produces BuildOutput\packaging\Release\tools)
Build.cmd product

:: 2. pack into ..\..\PackageStore
build\xamlcompiler-nupkg\pack.cmd
```

`~\.nuget\packages\<id>\<version>` is immutable as far as NuGet is concerned: repacking the same
version is silently ignored in favour of the cached copy, so bump the version on every iteration
(`pack.cmd -p:PackageVersion=3.0.0-dev.1`) or delete the cached folder and restore again.

Incremental builds decide whether to re-run XAML compilation from a fingerprint of the XAML files,
references and local assemblies - **not** of the compiler binaries. Always delete `obj\` and `bin\`
after switching or repacking the compiler, otherwise output from the previous compiler is reused.

#### Status
- Build: 0 errors; every generated file carries the `3.0.0.0` stamp; `App.xbf`, `MainWindow.xbf` and
  `ProgressDialog.xbf` are produced.
- The assembly entry point is the generated `BatchFfmpegWinUI.Program.Main`; the project has no
  `Program.vb`.
- Run: the window is created and stays up (caption `WinUI 3 VB Demo - mp4 converter`).
- Differential build against the stock compiler: differences are limited to the entry point block
  (the fork emits `Public Module Program` with `Sub Main` plus the `#If DISABLE_XAML_GENERATED_MAIN`
  helpers, the stock emits `Public Class Program` + `Sub Program` with `<MTAThread()>`) and the
  `GeneratedCodeAttribute` version string; `XamlTypeInfo.g.vb` is otherwise byte-identical.

#### Known gaps
- `ProgressDialog.xaml` compiles (generated sources, `ProgressDialog.xbf`, type present in the
  assembly) but is not exercised interactively.
- The Visual Studio / desktop MSBuild path is not exercised; verification uses `dotnet build`.
- `-p:VBWinUI3XamlCompilerEnabled=false` does not build this sample: the stock VB generator emits
  `Public Class Program`, which neither provides an entry point nor coexists with the injected
  `Program` module (`BC30179`). The switch is only useful for comparing generated sources.
